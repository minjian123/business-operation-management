## 1. 目的与范围 <a id="purpose"></a>

把 biz 全部文档的接入形态口径从「平台扩展（进程内扩展包、运行时并入平台进程）」统一改写为「**产品服务（独立服务）**」，并按 bms 服务目录对齐五模块服务标识；同时建立 biz 项目阶段体系作为后续接入开发的基线。

- 权威依据：bms《微服务演进规划》（服务清单第 3 批、仓库形态 2.3）、《平台可扩展性规划》「业务承载路径的取舍」「独立服务形态口径」节、《架构设计 · 模块注册》「服务目录与契约登记」「独立接入边界」节（`bms文档/…`）；
- 范围外：代码接入（待 bms R4.1~R4.3）、业务域候选实施。

## 3. 口径对照（旧 → 新） <a id="mapping"></a>

| 维度 | 旧口径 | 新口径 |
| --- | --- | --- |
| 接入形态 | 平台扩展：后端扩展包并入 bms 进程、前端模块构建期合并 | **产品服务（独立服务，默认）**：后端按业务域拆服务独立部署、每服务独立库 × 每租户；前端以 **Module Federation 运行时模块**接入（构建期合并为过渡） |
| 平台集成 | 进程内直接复用 | 经 **OIDC 认证 + `/api/open` + 事件**复用平台能力 |
| 登记机制 | 平台 `sys_module` 模块注册（表前缀 / 业务码 / 错误码段 / 事件域） | **服务目录与契约 / 版本登记**（`sys_module` 升格；注册要素不变，增服务标识与契约版本，破坏性变更按 oasdiff 门禁） |
| 服务标识 | `pur_service` / `pay_service` … | 服务目录 `service_key`：`pur` / `pay` / `sale` / `wh` / `sup`（`product_key=biz`，bms 服务目录 `planned` 行） |
| 数据形态 | 业务表落租户库 | **每服务独立库**（服务化地基 S2）；跨服务读走契约 / 只读投影，禁跨库 JOIN |
| 强隔离形态 | 「独立服务」轨为强隔离场景另计 | **产品服务为默认轨**；「外部独立服务」轨（异构 / 外部团队强隔离系统，OIDC + `/api/open` + 外链菜单）另计 |
| 部署 | 随平台 Docker Compose 一体化部署 | 产品服务独立部署（Compose 多容器 → 迁 k3s 同模型），经网关统一入口 |

## 4. 边界与开放项 <a id="boundary"></a>

- bms 服务目录 biz 五行为 `planned`（未建表、未接服务）；biz 代码接入随 bms R4.2 启动时另立阶段，本任务只对齐文档与登记口径；
- 服务工程名、目录结构按 bms《后端开发规范》与 `new_service.py` 同构骨架在代码阶段确定；
- 前端模块契约、模块清单按 bms 阶段五已落地形态执行（Module Federation 宿主 / 远端约定）。

## 5. 验证方式 <a id="verify"></a>

1. 关键词扫描：`并入平台进程`、`扩展包`（指后端运行时）、`pur_service`、`构建期合并`（作为主形态）在 biz 文档中归零（历史/范围外表述除外）；
2. 相对链接校验：本次新增与新改链接可达（含 `../bms文档/…` 与阶段内互链）；
3. 与 bms 服务目录 / 微服务演进规划逐项核对服务标识、库形态、登记口径。

> 依 bms《任务文档规范》《文档生成规范》编写 · 设计变更须先回写本设计再实施
