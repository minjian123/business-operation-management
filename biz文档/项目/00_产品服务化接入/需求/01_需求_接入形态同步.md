# 接入形态同步 · 需求域

> biz 项目 00 阶段 · 需求域 01

[需求总览](00_需求_产品服务化接入.md) › 01-接入形态同步

## 1. 域说明 <a id="intro"></a>

本域承载 bms 微服务改造定案后 biz 侧的接入形态对齐需求：把 biz 全部文档中的「平台扩展（进程内扩展包、运行时并入平台进程）」口径改写为「产品服务（独立服务）」，并将五模块服务标识与 bms 服务目录登记对齐；目标是 biz 后续接入开发（R4.2）启动时文档即为基线、无需再返工。

- 依据：bms《微服务演进规划》第 3 批产品服务、《平台可扩展性规划》「业务承载路径的取舍」「独立服务形态口径」节、《架构设计 · 模块注册》「服务目录与契约登记」「独立接入边界」节（`bms文档/…`）；
- 覆盖范围：biz 规划、设计（架构 / 概要）、README、文档首页、本地规范。

## 2. 需求 01-1：产品接入形态文档同步 <a id="r01-1"></a>

优先级：2（高）

**背景与动机**：bms 于 2026-09-22 定案以微服务为目标架构——产品后端默认以独立服务接入（每服务独立库），进程内扩展包降为过渡形态；而 biz 文档（2026-09-10/11 编写）仍按「运行时并入平台进程」主叙事，与平台定案不一致；若不修正，AI 与开发者按旧口径推进设计与实现会造成返工。

**内容**（bms《微服务演进规划》第 3 批、《平台可扩展性规划》「业务承载路径的取舍」节）：

1. 修订《biz 企业运营管理规划》：项目定位、运行形态、技术基线、平台复用边界、演进路线、风险与对策；
2. 修订《架构设计 · 总览》：平台接入形态、数据与部署、数据与集成约定；
3. 修订《概要设计 · 总览》《采购管理》《收付款管理》中的「平台扩展应用」表述；
4. 修订 `README.md`、`文档首页.md`、《英文简称规范（biz）》中的产品形态表述。

**完成标准**：biz 全部文档中无「运行时并入平台进程」「扩展包并入」等旧主叙事残留；接入形态统一为「产品服务（独立服务）：后端按业务域拆服务独立部署、每服务独立库，前端以运行时模块接入，经 OIDC + `/api/open` + 事件复用平台能力」；文档链接自洽。

**参考文档**：bms《微服务演进规划》第 2.3 节与第 3 批；bms《平台可扩展性规划》「业务承载路径的取舍」节；bms《架构设计 · 模块注册》「独立接入边界」节。

## 3. 需求 01-2：五模块服务标识与服务目录登记对齐 <a id="r01-2"></a>

优先级：2（高）

**背景与动机**：bms 服务目录（`sys_module` 升格）已登记 biz 产品服务行（`service_key` = `pur`/`pay`/`sale`/`wh`/`sup`，`product_key=biz`，状态 `planned`）；biz 架构文档「后端服务」列仍写 `pur_service` 等，数据形态仍写「业务表落租户库」，与「每服务独立库」「服务标识即服务目录登记值」口径不一致，接入时需再对一轮。

**内容**：

1. 《架构设计 · 总览》「模块注册与标识」表：后端服务列改为服务标识（`pur` / `pay` / `sale` / `wh` / `sup`），与 bms 服务目录 `service_key` 一致；
2. 数据形态表述改为「每服务独立库 × 每租户」（bms 服务化地基 S2），跨服务读走契约 / 只读投影；
3. 登记口径表述改为「服务目录与契约 / 版本登记」（含服务版本与契约版本，破坏性变更按 oasdiff 门禁）；
4. 规划「模块标识符登记」节与风险表同步该口径。

**完成标准**：五模块的服务标识、库形态、登记口径三处与 bms《微服务演进规划》《架构设计 · 模块注册》一致；无 `pur_service` 等旧服务名残留。

**参考文档**：bms《架构设计 · 模块注册》第 6 节；bms《微服务演进规划》第 2.1 / 2.2 节。
